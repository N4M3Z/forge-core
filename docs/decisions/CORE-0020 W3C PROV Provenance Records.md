# W3C PROV Provenance Records

## Context

After assembly (CORE-0018) and ref stripping (CORE-0017), there is no record of what sources produced a deployed file or how. The manifest (CORE-0019) tracks integrity but not lineage. Auditors need to verify that a security-critical instruction (e.g., a CVE-driven guardrail) was included in the deployed prompt.

## Considered Options

- **W3C PROV YAML** — `entity`, `wasDerivedFrom`, `wasGeneratedBy` concepts in YAML
- **SLSA in-toto** — full build attestation with signing (deferred to forge-audit)
- **Custom schema** — ad-hoc YAML with no standard alignment
- **No provenance** — rely on git history alone

## Decision

Chosen option: **W3C PROV YAML**, because it's a ratified W3C standard purpose-built for "entity X was derived from Y by agent Z." Generated by forge-cli at deploy time, not authored. External source URLs extracted from stripped GFM reference links (CORE-0017). Converts to JSON via `yaml to-json` for tooling interop.

```yaml
entity:
    name: AgentTeams.md
    sha256: b7d1e4...

wasDerivedFrom:
    - uri: rules/AgentTeams.md
      sha256: a3f8c2...
    - uri: rules/codex/AgentTeams.md
      sha256: c9e2f1...
      mode: append

wasGeneratedBy:
    builder: forge-cli@0.6.0
    time: "2026-03-15T01:00:00Z"
    provider: codex

sources:
    - https://cve.example.com/2026-1234
```

Recipe (directory tree + frontmatter) and provenance (this record) are separate concerns. The recipe is prospective ("take Y, apply Z"). The provenance is retrospective ("entity X was derived from Y by Z"). This file is the latter — generated after assembly, recording what happened.

## Consequences

- Positive: W3C PROV is a ratified standard, not a custom schema
- Positive: generated, not authored — zero maintenance burden for most rules
- Positive: extracted `sources:` provide audit trail to external authorities (CVEs, OWASP)
- Tradeoff: one `.prov.yaml` generated per deployed rule
